# 测试

## 运行

| 命令 | 作用 |
|---|---|
| `just test` | 全部测试：先是 Godot 的（约 2 秒）：数据检查、阵容码、战斗用例、单元测试、存档、回放检查、冒烟流程，运行中出现任何错误都算失败；设置和存档用测试专用的文件（`user://test_*`），跑完删掉，不读写玩家的存档。最后跑 `just rs-test` |
| `just rs-test` | Rust 版结算的测试（`engine/`）：读同一份规则用例和冒烟用例，都检查左右对称；`VERSION` 和 `BattleSim.VERSION` 一致。没装 Rust 时提示去装 rustup |
| `just diff-sim [场数]` | 对拍：同一批随机对局（固定种子，一半机制密集）分别用 Godot 和 Rust 版跑，逐场比较，默认 100 万场（约 45 秒）；不一致时指出第一处不同的步骤。加 `--cards <文件>` 可以带上额外的卡（还没写进正式数据的数值和机制）。见 `engine/README.md` |
| `just record` | 用当前引擎重录规则用例的期望值，并列出结果变化的用例 |
| `just gen-random` | 重新生成冒烟用例里的随机对局（固定种子） |
| `just levels` | 枚举两个关卡的全部摆法，打印解，并把解写入冒烟用例 |

- Godot 路径默认是 `/Applications/Godot.app/Contents/MacOS/Godot`，可以用环境变量 `GODOT` 覆盖。
- CI（`.github/workflows/test.yml`）目前已停用（见 `docs/decisions.md` 11-06），提交和合并前在本地运行 `just test`。
## 测试项（`run_tests.gd`）

| 测试 | 内容 |
|---|---|
| 数据检查 | 卡牌、种族、时机、词条、关卡都有中文名，时机和词条都有说明（在英文环境下检查，确认能回退到中文）；基础技能和词条都有飘字的饰板贴图；翻译表的每个字都在子集化的字体里（缺了运行 `just fonts`）；卡名互不重复、不和别的卡的 id 相同、不含 `+` `/` 和全角的 `＋` `／`（阵容码按卡名认卡）；列出还没有卡图的卡，不算失败。数据字段和 id 的合法性由 `CardDB`、`LevelDB` 加载时校验 |
| 阵容码 | `cases/lineup_codes.json` 的用例（正式卡）逐条核对：写出的文字、读回的卡位和问题，写出的再读回来不变；"加人、改人之后"的用例（`setup`）临时改卡牌数据或翻译，核对完撤销。全部卡各写一次再读回来 |
| 战斗用例 | 直接调 `BattleSim`，用例见下一节。规则用例的结果符合期望，只用测试卡；冒烟用例里关卡的解要赢。都检查交换左右后对称、事件日志自洽（按效果推演的战力、判死和最终结果都对得上，伤害的 `by` 指向正确的一方） |
| 单元测试 | 对战用例触发不到的情况，用测试卡：相邻两个单位同时阵亡、湮灭、格子模型（含一格多个时机、千机之匣的翻倍和千机魔女的倍数、卡面印的数）、结算加成记下来源、卡牌数据的校验（`cases/card_checks.json`）、回放依赖的事件细节（多一次的标记、多一轮的来源、协战按位置分开、神佑给的层数、美杜莎只清前两位、尤姆卡克斯加到哪些技能、萨满等两下都结算完才改数值、对方结算时己方全体加的每一条、致命伤害打免疫致命和战前减半的标记、鹦鹉获得之后的基础技能）、卡面文字、战斗中特殊技能栏（庇护剩余层数标紫、用完移除）、和卡面印的不同的基础技能标紫、飘字一加进来就摆在卡上（不在左上角闪一下） |
| 存档 | 设置读写往返、不合法的值用默认值；进度读写往返、再次通关不改第一次的时间；正式文件坏了用备份恢复（坏文件改名为 `.broken`，之后写入不覆盖备份）；备份也坏了从空进度开始；比游戏新的版本能读、只读不写 |
| 回放检查 | 战斗场景最后显示的胜负和幸存的角色、战力、基础技能和特殊技能（卡面的实时状态、中间的胜负文字）与 `BattleSim` 一致，点卡查看的战斗力和场上一致，结束后不留下飘字和亮起的卡：动画播完、僵持压缩、中途跳过、唤醒和队长蟾蜍、3★ 以上的机制（神佑、协战、免疫致命、多一次、多一轮一组，获得、复制、清除、改数值、炼药师、神裁者、沼泽之王一组，数值校正加的新机制一组：触发时该角色加、结算时加、对方结算时加、人数劣势全体加、致命伤害和免疫、战前减半、自身和前一位多一轮；都用正式卡，都要出现，没出现就提示换阵容）；测回放时长的模式（`cli/replay_time.gd`）一次播完、各时点加起来等于总时长 |
| 冒烟流程 | 从主菜单走一遍设置、科研模式、两个关卡、图鉴，全程不报错；其中的战斗也做回放检查。启动时存档坏了主菜单弹通知；设置改了立刻保存；进入科研模式、构筑阶段时紧凑模式是默认值，临时切换后打完一场回来保持；开战速度是默认值，速度按钮按 1×、2×、5×、20×、0.5× 循环（默认改成了 0.5×）；虎虎生风用能赢的摆法（`WINNING`；猪突猛进在数值校正后无解，待重做），赢了才记通关，关卡选择的已通关样式和存档一致；紧凑模式下手牌不压住右列；清除闯关记录（确认框）后都不显示已通关。科研模式检查右列不压住选卡区（紧凑模式开和关）、选卡、种族筛选只对角色（勾了种族后装备页照常显示）、从选卡区拖出不留影子、拖动互换、拖出移除、交换双方、清空和开战前的提示，以及阵容码面板（打开时是选中卡位的一方；复制、清空、再导入和原来一样；导入到已有阵容的一方先确认，取消不变；带问题的文字认不出的卡位空着、说明列在文本框下面；一个角色都认不出时不导入；切换一方；点框外、右上角的叉都能关闭）；关卡选择检查展开、收起详情；图鉴检查筛选（组内任一、组间同时满足）、排序和点卡放大。第一关还会按 `docs/design/game-design.md` 第 7 节逐条检查布阵交互（直接调用拖放逻辑，不经过鼠标），以及整理手牌 |

## 用例 `cases/`

| 文件 | 内容 | 维护方式 |
|---|---|---|
| `cards.json` | 测试卡，格式同 `data/cards.json`，id 以 `t_` 开头，序号都是 0。`t_<正式卡 id>` 是按复制时（2026-11）正式卡的数值复制的，以后正式卡调数值，测试卡不变；其余是为某条规则专门做的（如打全体的 `t_annihilator`、`t_wrecker`，致命伤害的 `t_executioner`） | 只加不改：改了数值会影响用到它的用例。效果改名、改写法时跟着改写法 |
| `battles.json` | 规则用例，只用测试卡，期望值是完整的结果。Rust 版（`engine/core/tests/cases.rs`）读同一份 | 规则改变时 `just record`，逐条核对变化 |
| `card_checks.json` | 卡牌数据的校验：每条一张卡，`ok` 为真的要通过，其余要在加载时报错（每种不合法的写法一张）。Godot 和 Rust 版的单元测试都读它，保证两边校验的情况一样 | 校验规则变化时增删 |
| `smoke.json` | 冒烟用例，用正式卡，只检查能打完、左右对称、事件自洽：关卡的全部解（`level-`，还要我方胜）和固定种子的随机对局（`random-`） | `just levels`；卡牌增删后 `just gen-random` |
| `lineup_codes.json` | 阵容码的用例（不是战斗用例，只有 Godot 读），用正式卡，`case` 是计划 `docs/plans/lineup-code.md` 第 3 节的编号，一个编号可以有几项：`lineup` 和 `text` 是写出的文字；`text`、`slots`（前几个卡位，其余为空）、`problems` 是读回的结果；`setup` 是前提（`add` 加卡和 `names` 卡名、`change` 改字段、`remove` 删卡、`rename_id` 改 id、`locale` 换语言） | 用例是设计的一部分：先改 `docs/design/lineup-code.md`，再改用例。用到的卡改名时跟着改 |

用例文件是 JSON 数组，一行一条：

```json
{"id": "rule-rally", "note": "说明", "p1": [["t_soldier", ""], ["t_soldier", ""]], "p2": [["t_pixie", ""]],
 "expect": {"winner": 1, "reason": "wipe", "p1": [["t_soldier", 1], ["t_soldier", 3]], "p2": []}}
```

- `p1`、`p2`：双方阵容，`[角色 id, 装备 id]`，装备为空字符串表示不带。
- `expect`：`winner` 是 1/2/3 = P1 胜 / P2 胜 / 平局；`reason` 是 `wipe`（全灭）或 `no_death`（连续 20 次交战无人阵亡）；`p1`、`p2` 是双方幸存的角色和战斗力，按队列顺序。冒烟用例只有关卡的解有 `expect`，而且只有 `winner`。
- 规则用例的 id 以 `rule-` 开头；`docx-`、`design-` 是早期战斗流程文档的例子和 1★ 的循环克制（数值是测试卡的）。

## 维护原则

- **改了规则**：运行 `just record`，逐条核对结果变化的用例都在预期范围内；再照着改 Rust 版，`just rs-test` 通过、`just diff-sim` 零差异，一起提交。
- **规则文档里的每个例子、每条口径都要有规则用例**；新机制先做测试卡和用例，不等正式卡。
- **保持精简、有代表性**：一条规则一条用例；新增用例前先看现有用例是否已经覆盖；删掉被别的用例完全覆盖的冗余用例。
- **只有对战用例触发不到的情况**才写单元测试。
