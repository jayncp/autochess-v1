# 测试

## 运行

| 命令 | 作用 |
|---|---|
| `just test` | 全部测试，约 2 秒：数据检查、战斗用例、单元测试、存档、回放检查、冒烟流程。运行中出现任何错误都算失败。设置和存档用测试专用的文件（`user://test_*`），跑完删掉，不读写玩家的存档 |
| `just record` | 用当前引擎重录规则用例的期望值，并列出结果变化的用例 |
| `just gen-random` | 重新生成冒烟用例里的随机对局（固定种子） |
| `just levels` | 枚举两个关卡的全部摆法，打印解，并把解写入冒烟用例 |

- Godot 路径默认是 `/Applications/Godot.app/Contents/MacOS/Godot`，可以用环境变量 `GODOT` 覆盖。
- CI（`.github/workflows/test.yml`）目前已停用（见 `docs/decisions.md` 11-06），提交和合并前在本地运行 `just test`。
## 测试项（`run_tests.gd`）

| 测试 | 内容 |
|---|---|
| 数据检查 | 卡牌、种族、时机、词条、关卡都有中文名，时机和词条都有说明（在英文环境下检查，确认能回退到中文）；基础技能和词条都有飘字的饰板贴图；翻译表的每个字都在子集化的字体里（缺了运行 `just fonts`）；列出还没有卡图的卡，不算失败。数据字段和 id 的合法性由 `CardDB`、`LevelDB` 加载时校验 |
| 战斗用例 | 直接调 `BattleSim`，用例见下一节。规则用例的结果符合期望，只用测试卡；冒烟用例里关卡的解要赢。都检查交换左右后对称、事件日志自洽（按效果推演的战力、判死和最终结果都对得上，伤害的 `by` 指向正确的一方） |
| 单元测试 | 对战用例触发不到的情况，用测试卡：相邻两个单位同时阵亡、湮灭、格子模型（含一格多个时机、千机之匣和千机魔女的翻倍、卡面印的数）、结算加成记下来源、回放依赖的事件细节（多一次的标记、多一轮的来源、协战按位置分开、神佑给的层数、美杜莎只清前两位、尤姆卡克斯加到哪些技能、萨满每一下之后改数值）、卡面文字、战斗中特殊技能栏（庇护剩余层数标紫、用完移除）、和卡面印的不同的基础技能标紫 |
| 存档 | 设置读写往返、不合法的值用默认值；进度读写往返、再次通关不改第一次的时间；正式文件坏了用备份恢复（坏文件改名为 `.broken`，之后写入不覆盖备份）；备份也坏了从空进度开始；比游戏新的版本能读、只读不写 |
| 回放检查 | 战斗场景最后显示的胜负和幸存的角色、战力、基础技能和特殊技能（卡面的实时状态、中间的胜负文字）与 `BattleSim` 一致，点卡查看的战斗力和场上一致，结束后不留下飘字和亮起的卡：动画播完、僵持压缩、中途跳过、唤醒和队长蟾蜍、3★ 以上的机制（神佑、协战、免疫致命、多一次、多一轮一组，获得、复制、清除、改数值、炼药师、神裁者、沼泽之王一组，都要出现，没出现就提示换阵容）；测回放时长的模式（`cli/replay_time.gd`）一次播完、各时点加起来等于总时长 |
| 冒烟流程 | 从主菜单走一遍设置、科研模式、两个关卡、图鉴，全程不报错；其中的战斗也做回放检查。启动时存档坏了主菜单弹通知；设置改了立刻保存；进入科研模式、构筑阶段时紧凑模式是默认值，临时切换后打完一场回来保持；开战速度是默认值，速度按钮按 1×、2×、5×、20×、0.5× 循环（默认改成了 0.5×）；第一关用能赢的摆法（`WINNING`），赢了才记通关，关卡选择的已通关样式和存档一致；紧凑模式下手牌不压住右列；清除闯关记录（确认框）后都不显示已通关。科研模式检查选卡、从选卡区拖出不留影子、拖动互换、拖出移除、交换双方、清空和开战前的提示；关卡选择检查展开、收起详情；图鉴检查筛选（组内任一、组间同时满足）、排序和点卡放大。第一关还会按 `docs/design/game-design.md` 第 7 节逐条检查布阵交互（直接调用拖放逻辑，不经过鼠标），以及整理手牌 |

## 战斗用例 `cases/`

| 文件 | 内容 | 维护方式 |
|---|---|---|
| `cards.json` | 测试卡，格式同 `data/cards.json`，id 以 `t_` 开头，序号都是 0。`t_<正式卡 id>` 是按复制时（2026-11）正式卡的数值复制的，以后正式卡调数值，测试卡不变；其余是为某条规则专门做的（如打全体的 `t_annihilator`、`t_wrecker`） | 只加不改：改了数值会影响用到它的用例 |
| `battles.json` | 规则用例，只用测试卡，期望值是完整的结果。以后 Rust 版读同一份 | 规则改变时 `just record`，逐条核对变化 |
| `smoke.json` | 冒烟用例，用正式卡，只检查能打完、左右对称、事件自洽：关卡的全部解（`level-`，还要我方胜）和固定种子的随机对局（`random-`） | `just levels`；卡牌增删后 `just gen-random` |

用例文件是 JSON 数组，一行一条：

```json
{"id": "rule-rally", "note": "说明", "p1": [["t_soldier", ""], ["t_soldier", ""]], "p2": [["t_pixie", ""]],
 "expect": {"winner": 1, "reason": "wipe", "p1": [["t_soldier", 1], ["t_soldier", 3]], "p2": []}}
```

- `p1`、`p2`：双方阵容，`[角色 id, 装备 id]`，装备为空字符串表示不带。
- `expect`：`winner` 是 1/2/3 = P1 胜 / P2 胜 / 平局；`reason` 是 `wipe`（全灭）或 `no_death`（连续 20 次交战无人阵亡）；`p1`、`p2` 是双方幸存的角色和战斗力，按队列顺序。冒烟用例只有关卡的解有 `expect`，而且只有 `winner`。
- 规则用例的 id 以 `rule-` 开头；`docx-`、`design-` 是早期战斗流程文档的例子和 1★ 的循环克制（数值是测试卡的）。

## 维护原则

- **改了规则**：运行 `just record`，逐条核对结果变化的用例都在预期范围内，再和改动一起提交。
- **规则文档里的每个例子、每条口径都要有规则用例**；新机制先做测试卡和用例，不等正式卡。
- **保持精简、有代表性**：一条规则一条用例；新增用例前先看现有用例是否已经覆盖；删掉被别的用例完全覆盖的冗余用例。
- **只有对战用例触发不到的情况**才写单元测试。
