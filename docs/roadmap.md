# 路线图

> 活文档，随项目推进更新。当前进度见 [../PROCESS.md](../PROCESS.md)，已拍板事项见 [decisions.md](decisions.md)。
> 每个阶段开始前，在 `docs/plans/` 写计划给用户过目，确认后开 issue，在分支上开发，通过 PR 合并；小修改直接提交到 main。

## 阶段 0：仓库初始化

- `git init -b main`，远程仓库 `https://github.com/jayncp/autochess-v1.git`（公开），用本机 git 全局身份提交。
- 协议文件：
  - `LICENSE`：AGPL-3.0；
  - 美术、数据、文档：CC BY-SA 4.0 说明；
  - 字体：OFL 许可文本。
- 仓库 README：项目简介、运行方式、各部分适用的协议。
- `.gitignore` 补上 `.DS_Store`。`.godot/` 已被忽略，签名密码在里面，不会进库。
- 首次提交是接手时的原样快照（含 docs），之后的改动都在它上面做。

## 阶段 0.5：行为基线与规则修复

目标：之后整理和重构时，能证明"行为没变"或"只在预期的地方变了"。

1. **测试入口**：`tests/` 下放无头 GDScript 测试脚本，先不引入第三方框架。新增 `justfile`，提供 `just run`、`just test`、`just smoke` 等命令。
2. **用现状生成基线**：
   - 战斗黄金用例：给定双方阵容，期望得到胜负和每个幸存单位的最终战力。
     - 每个词条、时机、装备叠加规则各几条用例；
     - docx 里的例子和 1★ 对局矩阵；
     - 两个关卡的默认摆法和已知解；
     - 约 300 条固定种子的随机对局。
   - 冒烟测试：每个场景都能加载；从主菜单进各模式、进战斗、再返回，全程无报错。
   - 用现有的战斗场景无头跑，约 30 场/秒，几百条用例十几秒。
3. **逐项修复**，每项单独提交，附"哪些用例的结果变了、为什么"的清单：
   - 反噬：双方都结算、走伤害流程；
   - 平局：新增"连续 20 轮无人阵亡"；
   - 死亡单位一次性移除；
   - 坚固求和；
   - 跳过时战前阶段仍有等待；
   - 数据：圣水改为仅战前时机 +2 战力。
4. 两个关卡的已知解：用户只记得可行解不多，去掉对称后大约 1–4 组。用枚举找出全部解作为基线，修复反噬前后对比解的数量和通过率；变化大的话和用户讨论怎么调这一关。

## 阶段 1：规范整理（不改功能）

### 1.1 英文 id

卡名现在同时充当数据 key、显示名、图片文件名和关卡引用，需要一次性迁移。英文 id 对照表在计划文档里给用户过目。

- **卡牌**：英文单词 snake_case，如 `soldier`、`tiger`、`fey_tiger`、`wooden_sword`、`spiked_gauntlet`；原数字序号保留为字段。
- **词条**：如 `assemble`（集结）、`rage`（狂暴）、`corrode`（腐蚀）、`inspire`（振奋）、`annihilate`（湮灭）、`wealth`（财富）、`lethal`（致命）、`sturdy`（坚固）、`backlash`（反噬）、`shelter`（庇护）。
- **时机**：`pre_battle`、`on_enter`、`on_engage`、`on_sell`。
- **种族**：`human`、`beast`、`nature`、`divine`、`elf`、`treasure`、`demon`。
- **关卡**：如 `boar_rush`（猪突猛进）。
- **资源**：卡图 `assets/cards/<card_id>.png`，背景 `bg_<场景>.png`，界面图 `ui_<名称>.png`。
- **节点名**：`实时状态` 等中文节点名改成英文。

### 1.2 数据外置

- `card_database.gd` 的 11 列匿名数组改为带字段名的 `data/cards.json`，关卡改为 `data/levels.json`。
- 由 `CardDB` 统一加载。Godot 和 Python 工具读同一份数据。

### 1.3 多语言预留

- 卡牌显示名和界面文字从代码、数据中分离，放进 Godot 的翻译表，目前只有中文一列。
- 代码里通过翻译 key 取文字，与内部英文 id 相互独立。

### 1.4 目录结构（按功能分组，脚本和场景放在一起）

```
autochess-v1/
├── assets/          cards/、backgrounds/、ui/、fonts/
├── data/            cards.json、levels.json
├── i18n/            翻译表
├── scenes/          main/、menu/、sandbox/（科研）、level/、battle/、book/、components/
├── scripts/         不依赖场景的逻辑：core/（战斗核心、CardDB）、util/
├── cli/             GDScript 无头命令入口：模拟、关卡验证等（godot --headless --script）
├── tools/           Python 工具（目录内放 .gdignore，Godot 不会扫描）
│   ├── pyproject.toml   用 uv 管理；重依赖（如 torch）放可选依赖组
│   └── ...              分析、报表、阵容码、调用 cli/ 批量模拟、以后的 RL
├── tests/
├── docs/
└── justfile
```

- **Python 和 Godot 放同一个仓库**：两边读同一份 `data/`，战斗规则只有 GDScript 一份实现，Python 通过 `cli/` 调用它。
  - Python 的 `.venv`、实验输出、RL 模型权重都不进 git；
  - 导出游戏时排除 `tools/`、`docs/`、`tests/`。
- **移动资源**：`.import`、`.uid` 文件要一起移，并改写 `.tscn` 里的路径，否则引用会断。用脚本批量做，之后跑导入和冒烟测试验证。
- **删除**：项目里未被引用的旧 UI 图（`卡槽.png`、`自走棋测试UI*.png`）。8 张生图过程图建议也移出项目（资源库里有一模一样的副本），执行前再确认。
- **顺手修的小 UI bug**：拖到敌方卡上的空指针、图鉴多出一页空页、飘字节点不释放。

**验收**：基线测试全部通过；用户手动把各模式玩一遍。

## 阶段 2：战斗核心

这是后续所有工作的地基：三星卡、关卡验证、平衡测试、AI、联机。先写设计文档给用户过目。

```
BattleSim（纯 GDScript RefCounted，不依赖节点）
  输入：双方阵容（card_id + equip_id）+ CardDB
  输出：结果 + 事件日志（技能、伤害、死亡……）
    ├── 战斗场景：按事件日志回放动画；"跳过"就是直接显示最终状态
    ├── cli/sim.gd：JSON 进、JSON 出，可批量
    └── tests/：基线不变 + 左右对称 + 战斗必然结束
```

- 词条和复杂效果用"时机钩子 + 效果处理器"注册，不在主流程里写特判，给三星/四星的机制预留位置。
- 实现湮灭；动画模式与跳过模式结算顺序不一致的问题，随着抽离自然消除。
- **工具**：
  - 关卡通过率枚举（重做 `single_loop_test_launcher`）；
  - 平衡实验：有效战力、对局矩阵、星级平衡，能复现 balance-report 里的数据；
  - 实测吞吐量，决定以后做 RL 时是否需要更快的实现。
- 用模拟器校准圣水的补偿数值。

## 阶段 3：卡牌补全

1. 三星/四星分档：按[有效战力目标均值](design/card-design.md#1-星级档位与有效战力)逐张定位、调整。
2. 补齐 1–2★ 的非经济卡（如空心），再做新的 3★/4★ 角色和装备，包括完整词条版圣水、覆盖型 3★ 装备。
3. 卡图：先讨论形象，再 codex 生图、抠图、导出（流程见 [takeover/06-assets.md](takeover/06-assets.md#6-后续-ai-生图建议codex-cli)）。
4. 战斗表现：词条图标、buff 状态显示、复杂机制的特效。

## 阶段 4：闯关模式

- 只用裸卡和装备，不含羁绊、升星、经济。
- **教学关**：每个词条一关，循序渐进。
- **解谜关**：先定名字或敌方阵容，估算我方可用卡，用工具验证通过率，再微调；报告通过率和解的数量。
- 关卡描述、提示、评价，进度存档与解锁。

## 阶段 5：冒险模式

连续对战 AI，赢金币，买角色和装备构筑。需要商店、经济、对手生成（用模拟器调难度）、局内存档。

- 局外规则重新设计，桌游版（[takeover/05](takeover/05-design-materials.md#2-局外循环规则规则xlsx--docx)）只作参考。
- 羁绊、升星、经济卡可能在这一阶段引入。

## 阶段 6：线下对战（局域网）

多人两两对战，期间构筑。用 Godot 高层多人 API（ENet），由主机做权威。战斗是确定性的，可以只同步阵容，各端本地模拟。

## 阶段 7：AI 与平衡工具

- AI 玩家：启发式 AI → 强化学习（需要高吞吐模拟器和 gym 风格接口）→ 接入大模型 API 模拟玩家。
- 平衡工具：卡牌胜率、出场率、阵容搜索。

## 功能待办（不排阶段）

- **阵容码**：
  - 两种格式可以互相转换：可读、可编辑的文本，以及压缩成一串、便于复制的文本；
  - 科研模式和其他模式的阵容编辑处加"导出"，科研模式加"导入"；
  - 用于复盘和交流。可以在阶段 1 数据外置之后的任意时间做。

## 平台：移动端优先，兼顾 PC

- **已定**：
  - 看卡：手机长按，PC 悬停；
  - 文字大小、屏幕比例适配放到美化阶段；
  - 渲染器暂不换；
  - iOS 到联机阶段再说。
- **开发方式**：日常在 PC 上开发调试，定期真机测试；尽早建好 PC 导出预设，两端都保持可构建。
- **以后要处理**：
  - 卡面以图标和数字为主：现在的 12px 技能字在手机上只有约 0.7mm 高；
  - 拉伸改为 `expand` 加锚点布局，适配刘海屏；
  - Android 加网络权限；
  - iOS 局域网广播可能要额外申请权限，备选方案是手动输入 IP 或扫码连接。

## 持续：美术与体验

- **装备图尺寸**：未装备时，装备卡上的装备图放大到卡图区域约 1/4；装备到角色上后缩成现在的角标。
- **卡面区分**：
  - 角色卡、装备卡用不同底色；
  - 不同星级用不同的边框和分割线；
  - 以后升星可以做闪卡；
  - 卡图区域按种族使用不同背景。
- **按钮等控件**更丰富，替换现在的默认样式。
- **战斗表现**：见阶段 3。
